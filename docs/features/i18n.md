# Mehrsprachigkeit (Deutsch und Englisch)

Ausführliche Referenz zur Sprache der Oberfläche: Nutzung, Aufbau der Sprachdateien, eine neue Sprache hinzufügen, das Prüfskript und die bekannten Grenzen. Für Entwickler gibt es zusätzlich die Konventionen direkt am Code in [`frontend/lager-ui/src/locales/README.md`](../../frontend/lager-ui/src/locales/README.md); die Bedienung im Alltag steht in [USAGE.md](../USAGE.md#sprache).

Die Weboberfläche ist **zweisprachig** (react-i18next): **Deutsch** ist die Standardsprache und die Quelle aller Texte, **Englisch** die vollständige Übersetzung. Die **Meldungen des Servers** (Fehlertexte der API) und die **Dokumentation** bleiben **deutsch**.

## Nutzung

- **Umschalter:** ein DE/EN-Umschalter sitzt in der **Seitenleiste** und auf der **Anmeldeseite** (vor dem Login). Der Wechsel gilt sofort, ohne Neuladen.
- **Wahl merken:** die bewusste Wahl liegt im Browser (`localStorage`, Schlüssel `lager.lang`, pro Browser und Gerät). Ohne gespeicherte Wahl folgt die Oberfläche der **Browsersprache** (`en-US` zählt als Englisch, jede andere Sprache als Deutsch). Die erkannte Browsersprache wird nicht gespeichert: wer ihr folgt, folgt ihr weiter.
- **Reihenfolge:** gespeicherte Wahl, dann Browsersprache, dann Deutsch. Ist der Speicher gesperrt (privates Fenster), gilt die Wahl bis zum Neuladen.
- **Formate:** Datum, Uhrzeit, Zahlen und Beträge folgen der Sprache (Deutsch `de-DE`, Englisch `en-GB`: Tag zuerst, 24-Stunden-Uhr, Euro als "€"). Zeitstempel der API sind UTC und erscheinen in der Ortszeit des Browsers. Das Attribut `lang` von `<html>` folgt der Sprache.
- **Server:** die API kennt keine Spracheinstellung. Es gibt keinen Header und keinen Parameter, der Antworten übersetzt.

## Aufbau der Sprachdateien

Die Texte stehen nicht im Code, sondern je Bereich (Namespace) in JSON-Dateien unter `frontend/lager-ui/src/locales/<sprache>/<namespace>.json` und werden mit `t('namespace:schluessel')` benutzt (in JSX mit `<Trans>`). Es gibt **22 Namespaces** je Sprache:

| Gruppe | Namespaces |
|---|---|
| Allgemein | `common` (Schaltflächen, Laden und Leer, Scanner), `nav` (Seitenleiste, Suche, Sprache, Farbschema), `auth` (Login, Passwort), `errors` (Fehlertexte, Fehlercodes, Fehlerseiten), `status` (Anzeigenamen der Statuswerte) |
| Stammdaten | `articles`, `customers`, `warehouse` (Lagerstruktur, Layout-Editor), `users` |
| Abläufe | `orders`, `stock`, `inbound`, `inventory`, `returns`, `purchasing`, `picking` (Picklisten, Packen, Mobile-Picker), `shipping` |
| Auswertung und System | `reports` (samt Audit), `traceability`, `importexport`, `labels`, `system` |

Alle `*.json` werden beim Start automatisch eingesammelt (`import.meta.glob` in `frontend/lager-ui/src/i18n/index.ts`): **ein neuer Namespace braucht nur zwei Dateien (de und en), keinen Code.** Die deutschen Dateien sind die Quelle und bleiben wortgleich zum früheren Stand; Übersetzungen entstehen daneben.

Grundregeln für neue Texte:

- Ein Text bekommt einen Schlüssel **in allen Sprachen** (`de` und `en`), nie nur in einer.
- Schlüssel immer mit Namespace schreiben (`t('orders:cancel.button')`); außerhalb von React (Stores, reine Logik) `import { t } from '../i18n'`.
- Platzhalter als `{{name}}`, Plural über `_one` und `_other`; keine Text-Verkettung im Code.
- Dynamische Schlüssel nur mit festem Präfix als Template-Literal (z. B. für Statuswerte), damit das Prüfskript sie als benutzt erkennt.

## Fehlertexte und Statuswerte

- **Backend-Meldungen bleiben deutsch** (auch die Standardmeldungen der Validierung). Die Oberfläche fängt häufige **Fehlercodes** des Servers ab (`code` im Fehlerformat, siehe [API.md](../API.md#fehlerformat)) und zeigt sie in der gewählten Sprache: die Tabelle steht im Namespace `errors` unter `codes`. In der deutschen Oberfläche hat der Text des Servers Vorrang und die Tabelle ist nur der Fallback; in anderen Sprachen ersetzt ein bekannter Code die deutsche Serverzeile. Ein unbekannter Code zeigt weiter das deutsche `detail` des Servers.
- **Statuswerte** (Bestellung, Sendung, Pickliste ...) haben ihre Anzeigenamen im Namespace `status`. Die farbigen Statusfelder (StatusPills) zeigen teils den **englischen Serverwert** (siehe Grenzen).

## Neue Sprache hinzufügen

1. Den Ordner `frontend/lager-ui/src/locales/<code>/` anlegen, alle Dateien aus `de/` hineinkopieren und übersetzen (gleiche Schlüssel, gleiche Platzhalter).
2. In `frontend/lager-ui/src/i18n/locale.ts` den Code in `SUPPORTED_LANGUAGES` eintragen und in `intlLocale()` die Locale für Datum und Zahlen ergänzen.
3. Den Namen der Sprache in `nav.json` unter `language.names.<code>` ergänzen (in allen Sprachen).
4. `npm run i18n:check` und `npm test` ausführen (beide im Ordner `frontend/lager-ui`).

Der Umschalter zeigt danach alle Sprachen aus `SUPPORTED_LANGUAGES` (eine Schaltfläche je Sprachcode). Die Dokumentation unter `docs/` und die Meldungen des Servers ziehen damit nicht mit um.

## Prüfskript

`npm run i18n:check` (im Ordner `frontend/lager-ui`, Skript `frontend/lager-ui/scripts/i18n-check.mjs`) prüft die Sprachdateien und beendet sich mit Exit-Code 1 bei Abweichungen. Dieselbe Logik läuft als Vitest-Test (`npm test`) und damit auch in der CI:

| Prüfung | Was sie findet |
|---|---|
| Parität | eine Sprache hat andere Namespaces oder Schlüssel als die Quelle `de` |
| Platzhalter | `{{name}}` je Schlüssel in `de` und `en` verschieden; leere Übersetzungen |
| Fehlende Schlüssel | im Code als `'namespace:schluessel'` benutzt, aber in `de` nicht definiert (die Oberfläche würde den Rohschlüssel zeigen) |
| Ungenutzte Schlüssel | in `de` definiert, im Code nirgends benutzt |

Der Code wird als Text durchsucht, nicht geparst: jedes String-Literal der Form `'namespace:pfad.zum.key'` mit bekanntem Namespace zählt als Benutzung. Ein eigener Test rendert die Hauptseiten auf Englisch und stellt sicher, dass kein deutsches Stichwort übrig bleibt.

## Grenzen

Was heute nicht oder nur eingeschränkt geht:

- **Meldungen des Servers und Dokumentation sind deutsch.** Nur die in `errors` → `codes` erfassten Fehlercodes erscheinen in der gewählten Sprache; jede andere Meldung der API bleibt deutsch, auch in der englischen Oberfläche. Die README.en.md ist eine Zusammenfassung, die Seiten unter `docs/` gibt es nur auf Deutsch.
- **StatusPills zeigen teils englische Serverwerte.** Die farbigen Statusfelder zeigen den Serverwert (z. B. `Received`, `Shipped`, `PartiallyReceived`) statt eines übersetzten Namens, auch in der deutschen Oberfläche; wer sie eindeutschen will, ändert die Werte unter `pill` in `frontend/lager-ui/src/locales/de/status.json` (und die Tests, die den Serverwert erwarten). Statustexte in Tabellen und Dialogen sind übersetzt.
- **Fehlercodes werden in Englisch verallgemeinert.** In der englischen Oberfläche ersetzt die Tabelle `errors` → `codes` bei bekannten Codes die deutsche Serverzeile durch einen **allgemeinen Satz**, auch bei den allgemeinen Codes: aus `validation_failed` wird "The input is invalid.", aus `not_found` "The record was not found.". Eine genauere Angabe des Servers, die nicht in der Feldliste steht (etwa welche Id unbekannt ist), erscheint dann nicht. Validierungsfehler **mit Feldliste** zeigen weiter die (deutsche) Liste des Servers.
- **`<Trans>` parst Datenwerte als HTML.** Texte mit Auszeichnung (`<strong>`, `<code>`, Links) nutzen die Komponente `<Trans>`. Setzt eine Seite dort einen Wert aus den Nutzerdaten ein (`values`, z. B. der Anzeigename des Benutzers in der Seitenleiste oder der Name in einem Löschdialog), wird der eingesetzte Text zusammen mit dem Satz als HTML gelesen. Enthält ein Datenwert den Tag-Namen einer an `<Trans>` übergebenen Komponente (z. B. `<strong>`), kann das die Darstellung stören oder die Seite in die Fehlerseite (ErrorBoundary) fallen lassen. Das ist aus der Abnahme bekannt und hier **nur dokumentiert, nicht behoben**.
- **Sprache je Browser:** die Wahl liegt im Browser, nicht im Benutzerkonto; ein anderes Gerät oder Browserprofil hat seine eigene Einstellung.
